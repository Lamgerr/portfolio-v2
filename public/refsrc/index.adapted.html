I started with code and stayed for the systems.

I've been building software since 2021. Somewhere along the way the part that hooked me changed. These days it's the architecture: how data flows, where failures happen, what breaks under load, and how you keep 100 ms latency at 10× traffic.

Shipping is the easy part. Keeping it running is the work.

With the right stack and decent taste, anyone can ship a feature. I've shipped plenty. What still takes real craft is building systems that don't fall apart under real users, edge cases, and 3 AM alerts — and that's the part I want to be known for.

Full-stack means the full problem.

I work across React / Next.js on the frontend, Node.js and Python on the backend, PostgreSQL and MongoDB for data, and Docker + Kubernetes for deployment. I've run infra on AWS, GCP, and Azure. The stack choice follows the problem, not the other way around.

I build the products I architect.

Three of the projects in my work went from whiteboard to production because I built them end-to-end: NexaHQ, MediCore, and StayOps. Architecture without implementation is just opinions. Building changes how I design systems. I know what "just add a cache" actually costs.

I'm based wherever the work takes me — Remote / Worldwide. When I'm not building, I'm reading about distributed systems, tinkering with electronics, or trying to explain why the cloud bill spiked again. I work hard for whatever I want.

Four things I do on every project.

I go after the real bottleneck, not the stated feature.

Most briefs describe a solution someone already committed to. The useful work happens when you find what's underneath it. On a clinic system, the brief was appointments. The actual problem was that doctors couldn't trust the data. No scheduling UI fixes that.

I'll push back, once, properly.

If I think an architectural decision is wrong I'll say so with a reason, and then I'll build what you decided. You're paying for my judgment, not my agreement. But it's your product, and I won't relitigate a call you've already made.

I build the error paths too.

Partial failures, network timeouts, stale cache, the job that ran twice. These are where systems actually break in production, and they're what every sprint retrospective is about. This is the part I'm stubborn about.

I hand over something operable.

Not just working code. Logs that tell you what happened, metrics that surface what's wrong, runbooks that explain what to do at 3 AM. If your on-call engineer has to guess, I haven't finished.
